Here is the review of the BAYESIANQC Postgres-only local/dev runtime cutover based on the provided packet.

### 1. Verdict
**approve-with-nits**

This is an exceptionally well-orchestrated cutover for a dev/local environment. The test harnesses properly isolate database instances across parallel workers, the rehearsal scripts are pragmatic and thorough in checking parameter alignment, and the application boundaries safely enforce the Postgres-only constraint.

### 2. Findings (Ordered by Severity)

**Severity: Medium (Maintainability Time-Bomb)**
* **File:** `migrations/versions/20260703_0001_initial_sqlmodel_schema.py`
* **Finding:** The migration dynamically resolves tables using `SQLModel.metadata.tables[name]`. If a model is deleted or renamed in a future PR, `metadata.tables` will no longer contain it, causing a `KeyError` during `alembic upgrade base:head` on fresh databases. Alembic migrations must be fully independent of the current codebase state so that intermediate schemas can be built and subsequently altered.

**Severity: Low (Transaction Context)**
* **File:** `app/migrations.py`
* **Finding:** `run_alembic_migrations` uses `with engine.begin() as connection:` which starts a transaction. Alembic's generated `env.py` also executes `with context.begin_transaction():`. In SQLAlchemy 2.0+, nesting `begin()` without explicitly configuring savepoints can sometimes raise an `InvalidRequestError`. Using `with engine.connect() as connection:` is generally safer for programmatic Alembic upgrades, allowing `env.py` to manage the transaction.

**Severity: Low (Rehearsal Sequence Crash)**
* **File:** `scripts/rehearse_sqlite_to_postgres.py` (inside `_reset_postgres_sequences`)
* **Finding:** `pg_get_serial_sequence('{name}', 'id')` returns `NULL` for tables that use non-serial primary keys (like UUIDs or Strings). If you ever add such a table, executing `setval(NULL, ...)` will crash Postgres and fail the rehearsal script. The `sequence_checks` function safely handles this via an `if sequence_name is None:` check, but `_reset_postgres_sequences` misses this guard.

**Severity: Nit (Postgres Identifier Casing)**
* **File:** `scripts/rehearse_sqlite_to_postgres.py` (inside `_reset_postgres_sequences`)
* **Finding:** Passing unquoted table names to `pg_get_serial_sequence('{name}', 'id')` will cause Postgres to automatically fold them to lowercase. While SQLModel defaults to lowercase names, if a camelCase table name is ever introduced, the sequence lookup will fail. Consider wrapping the parameter in double-quotes: `pg_get_serial_sequence('"{name}"', 'id')`.

### 3. Specific fixes required before the demo/job-search milestone
None of the above are hard blockers for the immediate local/dev demo, as they all function correctly under the current schema and execution flow.

However, before demonstrating or heavily iterating, it is highly recommended to:
1. Update `app/migrations.py` to use `engine.connect()` instead of `engine.begin()`.
2. Add the `NULL` check guard for `pg_get_serial_sequence` in `_reset_postgres_sequences`.

### 4. Remaining production/lab-readiness gaps (To be documented)
The `docs/LAB_READINESS.md` correctly captures the bulk of the missing production features (OIDC, backups, timezone hardening). I recommend appending the following technical debts to the documented gaps:
* **Migration Freezing:** The initial Alembic migration (`0001`) relies on dynamic `SQLModel.metadata.create_all`. Before production go-live, this migration should be refactored into static `op.create_table` statements (e.g., via `alembic revision --autogenerate`) to prevent future `KeyError` crashes when models are deprecated.
* **Foreign Key Constraints:** The initial schema generated by SQLModel may lack database-level foreign key enforcement for relations not explicitly configured with constraints in the Python metadata.
