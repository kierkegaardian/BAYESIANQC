## 🚨 P0 Blockers (Critical Deployment Failures)

### 1. Missing Command Execution / Dispatch Block in the Remote Helper
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)
* **Details:** The script defines all necessary helper functions (e.g., `deploy_release`, `reset_data`, `rotate_password`, `rollback`, `smoke_release`) but contains **no entry point or dispatch execution block** at the end. 
* **Impact:** When the host wrapper [scripts/demo_vps.sh](file:///home/user/.gemini/antigravity-cli/scratch/scripts/demo_vps.sh) invokes the remote script via SSH (e.g., `remote_run bash remote.sh deploy`), the remote host will create directories, parse the function definitions, and immediately exit with status `0` without executing any deployment steps.
* **Required Fix:** Add a dispatch case block at the end of the script:
  ```bash
  case "$COMMAND" in
    bootstrap|deploy)
      check_prereqs
      deploy_release
      ;;
    reset-data)
      reset_data
      ;;
    rotate-password)
      rotate_password
      ;;
    smoke)
      smoke_release "$(current_release)"
      ;;
    rollback)
      rollback
      ;;
    *)
      usage
      exit 2
      ;;
  esac
  ```

### 2. Dirty Worktree Check Halts Deployment Under Known Baseline
* **File:** [scripts/demo_vps.sh](file:///home/user/.gemini/antigravity-cli/scratch/scripts/demo_vps.sh) inside the [ensure_clean_release](file:///home/user/.gemini/antigravity-cli/scratch/scripts/demo_vps.sh) function.
* **Details:** The script checks `git status --porcelain` and exits with code `3` if the worktree is dirty.
* **Impact:** The deployment packet explicitly notes: *"Known baseline: worktree contains unrelated pre-existing dirty BAYESIANQC changes"*. Because this check is enforced, the operator cannot deploy the demo until they stash or commit their unrelated changes. (Note: `git archive` only packages committed `HEAD` files anyway, so uncommitted changes would not be deployed regardless).
* **Required Fix:** The operator must stash/commit local changes before running the script, or the script must support a `--force` or `--allow-dirty` flag to skip this check during developer/staging walkthrough rehearsals.

## ⚠️ P1 Blockers (Security & Operational Risks)

### 1. Docker Compose Interpolation Corrupts the Basic Auth Hash
* **Files:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [rotate_password](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)) and [deploy/demo-vps/Caddyfile](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/Caddyfile).
* **Details:** The bcrypt hash generated by `caddy hash-password` is written directly to `app.env` via `set_env BAYESIANQC_BASIC_AUTH_HASH "$hash"`. Bcrypt hashes contain multiple `$` characters (e.g., `$2y$10$...`).
* **Impact:** Docker Compose parses env files and treats the `$` character as a variable expansion indicator. It will attempt to interpolate `$10` and other components of the bcrypt hash, resulting in a corrupted hash being loaded into Caddy. Basic Auth logins will fail consistently.
* **Required Fix:** Escape the `$` signs as `$$` before writing the hash to `app.env`. In Bash:
  ```bash
  hash="${hash//\$/\$\$}"
  ```

### 2. Password Rotation Does Not Take Effect (Caddy is Not Reloaded/Recreated)
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [rotate_password](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The function updates the environment file but does not restart or force-recreate the `caddy` service.
* **Impact:** Caddy continues using the old environment hash until the next full deployment/restart. This contradicts the runbook in [docs/STAKEHOLDER_DEMO_VPS_DEPLOYMENT.md](file:///home/user/.gemini/antigravity-cli/scratch/docs/STAKEHOLDER_DEMO_VPS_DEPLOYMENT.md) which claims it *"force-recreates Caddy so the new password hash is active immediately"*.
* **Required Fix:** Retrieve the current release path and trigger a Caddy container recreate:
  ```bash
  local release
  release="$(current_release)"
  compose "$release" up -d --force-recreate caddy
  ```

### 3. Reset Data Cleanup Fails Due to Container Root Ownership
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [reset_data](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The script attempts to clean the import archive folder on the host using `find "$REMOTE_ROOT/import-archive" -mindepth 1 -maxdepth 1 -exec rm -rf {} +`. 
* **Impact:** The `api` container runs as root (no `USER` in [Dockerfile.api](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/Dockerfile.api)), which means imported files inside the mounted volume `/var/lib/bayesianqc/import-archive` are owned by `root`. A non-privileged deploy user running `remote.sh` will receive a "Permission denied" error during cleanup.
* **Required Fix:** Clean up the archive directory from within the container context:
  ```bash
  compose "$release" run --rm api sh -c 'rm -rf /var/lib/bayesianqc/import-archive/*'
  ```

### 4. Rollback Rebuilds Images and is Vulnerable to Network/Dependency Failure
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [rollback](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The `rollback` command runs `compose "$release" build`. The services [docker-compose.yml](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/docker-compose.yml) do not tag images with release IDs (defaulting to the `latest` tag).
* **Impact:** Rollbacks should ideally be instant metadata/symlink operations. Rebuilding on rollback requires network connectivity for `pip` and `npm`, making the rollback vulnerable to external network issues or dependency resolution failures.
* **Required Fix:** Tag built images with the unique release ID (e.g., `image: bayesianqc-demo-api:${BAYESIANQC_RELEASE_ID}`) so that old builds are preserved locally and rollbacks require zero building.

## ℹ️ P2 Findings & Recommendations

### 1. Potential Hairpin NAT / Loopback Blocks on Public Smoke Test
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [wait_for_public_basic_auth](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The public smoke test runs on the remote VPS host and attempts to resolve `https://qc.geoffsmiscellany.com/api/me` over the public WAN.
* **Impact:** Many VPS providers block loopback traffic to their own public IP interface, or hairpin NAT is disabled. The script will fail the public check even if the service is fully functional from the outside world.
* **Recommendation:** Move the public smoke check to the operator's machine (run it from [scripts/demo_vps.sh](file:///home/user/.gemini/antigravity-cli/scratch/scripts/demo_vps.sh) locally, not inside `remote.sh`).

### 2. Slow Container Wait Loops
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [wait_for_api](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) and [wait_for_caddy_basic_auth](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The script runs a 40-iteration loop that spins up a new `api` container on every iteration (`compose run --rm api python...`) to test the running API container.
* **Impact:** Spinning up containers sequentially is slow and resource-heavy.
* **Recommendation:** Use `compose exec -T api python...` to run the check directly inside the existing container without container instantiation overhead.

### 3. Prerequisite Checks are Unused Dead Code
* **File:** [deploy/demo-vps/remote.sh](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh) (within [check_prereqs](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/remote.sh)).
* **Details:** The `check_prereqs` function is defined but never invoked.
* **Recommendation:** Call `check_prereqs` at the beginning of `deploy_release` and `rollback` to fail fast if docker/docker-compose or dependencies are missing.

## 🔒 Coherence and Security Boundary Verification

* **Shell Quoting:** The usage of `shell_join` with `printf '%q'` ensures arguments passed over SSH are cleanly escaped and protected against command injection.
* **Docker/Caddy Exposure:** Ports for Postgres (`5432`) and API (`8010`) are not bound to host ports in [docker-compose.yml](file:///home/user/.gemini/antigravity-cli/scratch/deploy/demo-vps/docker-compose.yml) (exposed only within the bridge network), ensuring public traffic is routed exclusively through Caddy's HTTPS (`443`) and HTTP (`80`).
* **Basic Auth & API Key Boundary:** The architecture of Caddy validating browser Basic Auth credentials and then injecting the server-side admin API key (`X-API-Key`) for all `/api/*` requests is coherent for this *shared-admin stakeholder demo*. However, be aware that there is no multi-user isolation: anyone with the Basic Auth credentials has complete database read/write/delete authority.
* **Reset/Rollback Integrity:** Dropping and recreating the database via Postgres 16's `dropdb --force` / `createdb` works fine. However, database rollbacks/downgrades are not handled automatically; if a newer migration has altered the schema, rolling back to older code may cause schema mismatch errors unless `reset-data` is run.
* **Operator Runbook Clarity:** The runbook is exceptionally clear, correctly detailing the use-case boundaries and operational warnings.
